# ORB-SLAM2 基础是否解释了性能差异？

**与移植成本、适用场景有关，但不能解释 GF 内部 A/B 为什么没有得到预期加速。** GF01 和 GF02 的 baseline 与所有哈希组都来自同一 GF/ORB2 分支；版本在这些对照中没有变化，因此不存在可供估计的 ORB2→ORB3 版本效应。

## 源码确认的区别

| 层面 | GF 公开分支 / 本实验 | 当前运行用 ORB3 | 可得出的结论 |
|---|---|---|---|
| 前端链路 | 共视 KF → MP 集合 → 投影搜索 → 位姿优化；哈希路径在几何搜索前取交集 | RGB-D 同样具有这条主链路 | MIH 原理可以移植，接口与开销必须重测 |
| 局部跟踪最低内点 | GF 修改为 15，近期重定位 25 | 纯 RGB-D 常态 30，近期重定位 50；另有 RECENTLY_LOST 分支 | 较宽松门槛是 GF fork 的改动，不能当成 ORB2 固有特性 |
| 传感器实验 | 论文主要是单目；本实验 EuRoC 单目、TUM RGB-D VO | 板端目标纯 RGB-D，700 特征、5 层、ARM/ROS2 | 不能用桌面单目均值替代板端 RGB-D Callback P95 |
| 地图架构 | 原始指针、单 Map 为主 | Atlas、地图切换/合并、恢复状态；MEM18 所有权修复 | 哈希必须处理地图代次和对象失效，不能直接复制指针缓存 |
| LM01 工程 | 没有 LM01 的独立尝试/提交事务 | 候选路径增加快照、验证、提交、完整重试 | LM01 实测额外成本不是所有 ORB3 的固有成本 |
| IMU | 此处未启用 | 当前纯 RGB-D 不执行 IMU 优化 | 不能把纯 RGB-D 的慢归因于 ORB3 支持 IMU |
| 延时边界 | GF 在额外匹配和选表之前已有位姿输出位置 | 当前验收看完整回调 | 位姿可用延时和整帧处理时间需要分别测量 |

原版 ORB-SLAM2 的 `TrackLocalMap()` 仍为 30/50，源码可直接核对：[官方 Tracking.cc](https://github.com/raulmur/ORB_SLAM2/blob/master/src/Tracking.cc#L894-L902)。GF 的 15/25 来自本地固定来源的 `upstream/src/Tracking.cc`，不是本轮为提高通过率修改。ORB3 的新增视觉惯性与多地图能力见[官方说明](https://github.com/UZ-SLAMLab/ORB_SLAM3)。

当前 ORB3 对照路径：`/home/ywl/Project/RDK_X5_orb_slam/debug_branches/rgbd_memory_lifecycle/core/src/Tracking.cc`，`TrackLocalMap` 约 3485 行，RGB-D 成败门约 3624/3650 行。IDE 的 XFeat core 不是板端基线。本轮仅阅读该路径，未修改或部署。

DBoW2/DBoW3 主要影响词袋与检索相关路径；本次 MIH 位于局部点外观检索，不能仅以词典版本解释全部投影搜索时间。其独立贡献未测量。

## 可以与不可以归因的内容

GF02 用同构建方式、同数据、同匹配阈值比较三种哈希策略和关闭哈希，可判断这些策略在此条件下的效果。GF01→GF02 还增加了同步修复、计时和构建变化，历史绝对耗时不可直接作因果比较。

若要量化 ORB2 与 ORB3 本身的贡献，需要另做同硬件、同传感器、同输入、同特征/金字塔、同回环设置及同测量边界的四组测试：ORB2 off/on MIH 与 ORB3 off/on MIH。即便如此，地图演化和实现差异仍须联合看精度与失败率。本轮没有执行该跨版本实验，因此不报告“ORB3 导致了多少毫秒”的数字。

移植判断应先看局部搜索省下的时间能否覆盖维护、同步、后处理和生命周期成本，再看后段尾延时与精度；不能仅凭局部 MP 数减少，或某个完整 API 之前的计时点更快，就认定板端实时性问题解决。
